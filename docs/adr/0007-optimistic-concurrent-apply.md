# ADR-0007：正式应用的乐观并发控制与安全补偿

- 状态：已采纳
- 日期：2026-08-02
- 取代：[ADR-0005](0005-isolated-workspace-atomic-apply.md) 中的并发提交与补偿保证；其双快照和最终聚合 HITL 决策继续有效

## 背景

基线全量校验与逐文件 `os.replace` 之间存在 TOCTOU 窗口。另一个本服务 run、编辑器或
外部进程可在预检后修改目标；旧实现会继续替换，并在失败时无条件用备份回滚，可能先覆盖
新保存的内容，再覆盖事务期间出现的第三方修改。逐文件原子替换加补偿也不等价于真正的
多文件文件系统事务，不能宣称严格“全有或全无”。

## 决策

1. 按规范化 `CodeSmells` 根目录建立进程内互斥临界区。锁覆盖证据复核、全量预检、同目录
   临时文件准备、逐文件提交、冲突处理、补偿和临时资源清理。
2. 锁表采用引用计数：最后一个持有者/等待者退出时删除条目，避免不同临时源码根形成无边界
   进程级状态。同一根目录串行，不同根目录可以并行。
3. apply 继续复核 Reviewer 完整工作区摘要、最终审批摘要、baseline 快照和批准内容；锁不能
   代替证据链。
4. 全部目标先按 baseline 做一次预检。临时文件在目标同目录写入、fsync、关闭后进入提交。
5. 每个目标在实际替换前立即重算类型与 SHA-256；已存在、缺失、新建、删除以及文件变目录
   都必须仍与预期 baseline 一致。路径组件出现符号链接、junction 或 Windows reparse point
   时失败关闭。
6. 每次成功替换记录本事务写入状态：普通写入记录内容摘要，删除记录 `missing`。
7. 后续冲突或替换失败时逆序补偿。只有目标当前状态仍等于本事务写入状态才恢复备份或删除
   本事务新增文件。
8. 若第三方已再次修改，自动回滚不得覆盖它；错误返回 `rollback_status=partial`、冲突路径和
   恢复材料路径。原内容备份改名为同目录 `.refactor-recovery-<transaction_id>` 文件，由人工
   对照处理。普通成功、预检冲突和完整补偿不残留 prepared/backup 临时文件。

## 保证与边界

- 单文件替换使用同目录 `os.replace`，具有平台提供的单文件原子替换语义。
- 多文件通过乐观并发检查和补偿回滚提供应用级事务语义，不是文件系统或数据库的多文件
  原子事务，也不保证掉电恢复。
- 进程内锁只协调本服务实例；普通编辑器、其他进程和其他服务副本不会遵守它们。
- 每文件替换前的即时重检显著缩小但无法消除“最后一次读取到 `os.replace`”之间的竞态；
  补偿前同样存在极小窗口。若需要更强保证，应使用版本控制提交、支持事务的内容存储或
  操作系统级协作锁，并要求所有写入方遵守同一协议。

## 后果

正面：同进程 apply 不再交错；预检后的外部创建、删除、修改和路径类型变化可确定检测；
补偿不会静默覆盖第三方新内容；部分回滚具有结构化状态和最小恢复证据。

代价：提交需要重复读取和哈希文件；不同服务进程仍需外部分布式协调；极端竞态和掉电不能
获得数据库式原子保证；人工恢复材料需要运维确认后删除。
