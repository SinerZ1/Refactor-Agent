# ADR-0004：动态 DAG 的确定性串行调度

- 状态：已采纳
- 日期：2026-07-29

## 背景

Architect 能把跨文件重构拆成依赖任务，但如果计划只用于 Vue Flow 展示，执行仍是不可追踪的单次模型循环。另一方面，立即并行执行所有 ready task 会引入共享文件、交叉接口、checkpoint 合并和事件排序问题。

## 决策

- Architect 计划经严格 schema、路径、依赖和环校验后成为后端执行控制面。
- 调度器按计划原始顺序选择第一个 ready task，采用稳定串行拓扑执行。
- 状态中持久化任务状态、当前任务、完成集合、失败、重试次数和转换记录。
- Developer 每次只获得一个任务和唯一允许写入文件。
- 每个任务最多重试 3 次。
- Reviewer 可指定失败任务；该任务及传递下游被重开。
- 无 ready task 且仍有 pending task 时，将其标为 `blocked` 并失败。
- 计划缺失或非法时进入显式 `fallback`，保留旧单 Developer 主链。
- 前端只消费结构化 `plan.*`、`task.*` 和状态快照。

## 原因

确定性串行调度先解决“计划真正控制执行、失败可恢复、状态可审计”三个核心问题，同时避免并行写冲突。它也让离线 Eval 和 CI 能比较稳定事件序列。

## 后果

正面：

- DAG 不再只是可视化；
- 任务级失败、重试、阻断和预算都有明确终态；
- checkpoint 恢复只面对一个 active task；
- Reviewer 打回范围和事件顺序可重复。

代价：

- 独立 ready task 也不会并行，吞吐量较低；
- Architect 原始任务顺序会影响同层任务执行顺序；
- fallback 的能力低于有效 DAG；
- 后续并行化需要文件写集合、接口锁和状态合并协议。

## 被否决方案

- 仅前端 DAG：展示与实际执行不一致。
- 立即并行 ready task：在没有写集合和合并协议时风险过高。
- 模型自行决定下一任务：状态不可重复，失败传播难以验证。
