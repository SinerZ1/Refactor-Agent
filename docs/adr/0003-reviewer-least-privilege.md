# ADR-0003：Reviewer 最小权限

- 状态：已采纳
- 日期：2026-07-29

## 背景

Reviewer 需要判断候选变更是否通过，但“审查”并不天然要求任意读取或写入仓库。若 Reviewer 同时拥有源码读取、写入和自由命令能力，受到 Prompt injection 或模型幻觉影响时可能扩大数据暴露、修改证据或绕过职责分离。

## 决策

- Reviewer 唯一工具为 `run_unit_tests`。
- Reviewer 没有 `read_code_file`、`write_code_file` 或符号搜索工具。
- 测试工具只接受白名单逻辑套件，映射为固定 argv，并使用 `shell=False`。
- 控制面向 Reviewer 提供受控变更清单、最新变更摘要和结构化测试上下文。
- 成功路由同时要求 `【REFACTOR_SUCCESS】` 和确定性证据门禁。
- Reviewer 失败时以结构化 `failed_task_ids` 指定重开范围，由调度器执行，而不是 Reviewer 直接修改。

## 原因

职责分离让 Reviewer 只能产生“判决和证据”，不能改变被审对象。结构化上下文缩小信息面，测试工具提供可验证事实，最终人工聚合 diff 补充人类语义审查。

## 后果

正面：

- Reviewer 无法修改候选代码或测试结果；
- Prompt injection 的工具爆炸半径更小；
- 成功条件可由代码验证，不依赖自然语言可信度；
- Developer 写入后旧测试证据自动失效。

代价：

- Reviewer 无法主动探索未出现在变更清单中的影响面；
- 测试不足时不能证明完整业务正确性；
- Architect 的依赖分析和测试套件质量更重要；
- 最终人工 diff 仍是必要门禁。

## 被否决方案

- Reviewer 拥有只读仓库：信息更全，但扩大源码暴露面并模糊受控上下文边界。
- Reviewer 可修复代码：破坏作者/审查者职责分离，修改后还需再次审查。
- 仅依赖成功标记：模型可在未运行或测试失败时输出成功文本。
